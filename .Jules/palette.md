## 2025-05-15 - [DaisyUI Form Integration in Highly Custom Voice EFB Settings and Checklist Components]
**Learning:** Standard Tailwind utility form inputs (like simple input and select elements with manual borders and background rules) can result in visual inconsistencies across light and dark theme boundaries in a multi-themed system. Transitioning them to DaisyUI form selectors (`select`, `checkbox`, `range`) guarantees immediate theme integration while improving touch target compliance. Moreover, ensuring accessibility by explicitly linking labels via `htmlFor` attributes on all sliders, selects, and text inputs guarantees a screen-reader friendly and highly cohesive UX.
**Action:** Always prefer DaisyUI native semantic elements for form components, sliders, and checkboxes rather than writing arbitrary custom border/background utility overrides, and verify `htmlFor` pairing on every single interactive input.

## 2025-05-16 - [Tailwind Color Mapping and Custom Modal Refactoring for Theme Compliance]
**Learning:** In OryxOps, standard theme utilities (`bg-white`, `bg-gray-50`, `bg-gray-100`, etc.) are mapped to custom CSS variables via `style.css` to enable automatic light/dark mode adaptation. However, nested overlays or popups (like the fleet `BiddingModal`) often contain unmapped forced-dark utilities (`bg-gray-900`, `border-gray-800`), causing them to render in low-contrast dark themes during light mode. Transitioning them to the mapped theme-aware classes and adding standard accessibility behaviors (like `aria-label` for screen readers on icon-only actions) guarantees beautiful, accessible multi-theme layouts.
**Action:** Avoid hardcoded Tailwind dark classes (e.g., `bg-gray-900`, `border-gray-800`) in favor of mapped semantic classes (`bg-white` for cards/modals, `bg-gray-50` for inner sections) and ensure all modal dismissals possess descriptive ARIA tags.
